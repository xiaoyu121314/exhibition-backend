# P6S 工作人员识别与日去重客流方案可行性分析

<!-- @author MoShangHuaKai -->

分析日期：2026-11-05（Asia/Shanghai）。依据本次读取的项目源码、既有验证记录，以及本次实际读取的厂商公开文档。详细参数页中无法重新读取的内容单独说明。本报告不代表现场设备验收结果。

本次已由用户明确统计范围：**全部到访人员，包含未登记访客**。因此，只有工作人员识别或工作人员日去重完成，仍不满足完整需求。全部到访人员日去重的具体架构、实施条件和验收标准见第 8 节。

## 1. 结论与适用条件

方案的前半段有明确的协议和代码基础：后台维护工作人员，将照片与基础资料同步到设备，设备执行人脸比对，再向后台推送识别结果。当前项目已经实现人员同步和抓拍接收，但尚未接入设备识别结果，也没有人数统计功能。

“实时人流量按天去重”需要区分统计对象：

| 目标 | 可行性 | 主要条件或缺口 |
| --- | --- | --- |
| 后台工作人员资料与设备同步 | 代码已具备，现场链路待验收 | 已有照片规格、请求头和原生人员解析修正；既有记录未提供完整真实人员同步及识别成功证据 |
| 摄像头识别已登记工作人员并回传 | 协议可行，项目待开发 | 设备确实支持 FaceReco，开启识别和推送，完成回调身份映射 |
| 当天出现的工作人员去重人数 | 可行 | 按后台 staffId 和北京时间业务日期去重 |
| 进出人次统计 | 文档提供相应事件，项目未接入 | 设备具备客流能力，核实统计区间、方向和重传语义 |
| 区域内当前人数 | 文档提供相应事件，项目未接入 | 设备具备区域人数统计能力，按区域快照展示 |
| 未登记访客的全天去重人数 | 现有 HTTP 文档不足以证明可行 | 缺少跨次抓拍稳定身份，或可用的人脸特征与比较能力 |
| 设备直接上报“今日去重访客总数” | 未找到明确协议承诺 | 需要厂商提供对应固件能力、接口及实测证据 |

因此，工作人员同步及识别回传有实施基础；用户要求的全部人员全天去重仍缺少陌生访客身份来源。完整方案属于有条件可行，当前源码及已核实 HTTP 协议尚不足以交付该目标，不能仅增加一个计数接口完成。

## 2. 当前项目已经实现的部分

### 2.1 工作人员维护与设备同步

主要实现位于：

- `src/main/java/com/moshanghuakai/exhibition/staff/StaffService.java`
- `src/main/java/com/moshanghuakai/exhibition/staff/StaffDeviceSynchronizer.java`
- `src/main/java/com/moshanghuakai/exhibition/device/DeviceFaceClient.java`
- `sql/schema.sql` 中的 `exh_staff`、`exh_staff_device`。

现有顺序是：完整校验 → 同步设备 → 提交本地数据库事务；失败时执行设备补偿。启用人员会下发，停用或删除人员会移出目标脸库。后台保存工号、职位、部门和头像关联，设备主要接收姓名、性别和照片。设备身份通过 `exh_staff_device.face_uuid` 关联到本地 `staff_id`。

这是适合当前单实例、单同步设备的实现基础，但并非设备和 MySQL 的原子事务。设备写入后进程退出、本地提交失败且补偿失败、其他客户端改动设备等情况，仍可能造成两边不一致。当前没有后台自动对账和持久化同步重试；不能将成功补偿的模拟测试理解为任何故障下都能保证同步。

代码仅允许一台设备配置主动同步目标，身份关联表也以 `staff_id` 为主键。未来若同步多台设备，需要调整为一人多设备关联，并逐设备记录结果；这不属于当前最小实现的必要改动。

### 2.2 抓拍接收与事件幂等

`DeviceEventService.receive()` 当前只接受 `heartbeat` 和 `FaceSnapshot`，完成图片校验、文件保存、事件入库和 ACK。事件幂等键综合设备、事件类型、编号、时间、trackId 和图片摘要，能够拦截同一抓拍报文的重复提交。

这只能证明同一事件不会重复入库。一个人早上和下午分别被抓拍，会形成两个合法事件，不能据此得出两名访客。

### 2.3 识别与统计当前明确关闭

心跳响应将 `isPersonInfoEnable`、`isPassengerFlowStaticsEnable`、`isPeopleNumberStatisticsEventEnable` 均设置为 `false`。即使设备主动发送 FaceReco，当前服务也会以不支持的事件拒绝。

`ScreenController.overview()` 当前固定返回 `recognitionStatus=DISABLED`、`countMode=NONE`，工作人员、访客和总人数均为 `null`。`Models.Capture` 和抓拍表没有保存匹配人员、相似度或日去重身份。不能通过前端直接使用现有返回值完成人数展示。

`docs/verification.md` 也明确记录：此前已移除本地特征服务、向量匹配、识别任务、每日身份表和每日汇总表。

## 3. 厂商文档对每个环节的支持程度

### 3.1 人员下发有接口，真实新增仍有契约差异

厂商提供人员查询、资料修改、照片新增更新和删除接口。脸库操作需要管理凭据、拥有者生成的安全码以及配套时间。当前项目已经实现这些调用和身份关联。

存在必须真机确认的差异：本次读取的指导文档要求新增时传空 `FaceUUID`；仓库既有详细参数清单记录该字段不可为空。本次源码 `StaffDeviceSynchronizer.Change.apply()` 的 CREATE 分支实际传入 `UUID.randomUUID().toString()`，之后查询前后列表差异确定最终身份；而 README、接口清单和 `DeviceFaceClient.putPhoto()` 注释仍写空值新增。应以实际源码为准描述当前行为，并通过具体型号、固件确认新增契约、回读身份以及回调字段的对应关系。不能把这些互相不一致的说明当作已经通过真机验收的依据，也不能在超时后直接重复新增。[脸库管理指导](http://docs.p6sai.com/docs/cn/device/facemanage.html)、[照片新增更新参数入口，本次未重新验证参数正文](http://p6scgi-api.p6sai.com:4999/web/#/663863654/149227016)。

厂商指导还规定登记照片的尺寸与采样要求，并给出脸库容量说明。项目现已统一压缩工作人员照片，使用同一份 JPEG 字节落盘和下发；文档中的容量上限仍需结合具体硬件、内存和固件确认，不能直接当成现场设备承诺。[脸库管理指导](http://docs.p6sai.com/docs/cn/device/facemanage.html)。

项目现场记录显示，照片上传曾发生快速连接中断；后续先后处理了照片尺寸、multipart 外层 Content-Type 的 boundary 分隔空格以及设备原生人员缺少 FaceUUID 的解析问题。已有诊断响应和只读查询成功记录，仍未提供修正后真实工作人员新增、建模及识别回调的完整成功证据。客户端查询也未将返回的 `ModelState` 保存到人员对象；人员出现在列表中不能单独证明已经可以参与识别。[项目验证记录](verification.md)。

### 3.2 人脸识别回传是 FaceReco

识别结果事件为 `operator=FaceReco`。文档定义匹配数量、人员信息和匹配分数，并区分设备内身份与平台身份；未匹配时人员节点为空。因此可以用设备结果关联工作人员，但不能把未匹配事件自动变成一个有稳定身份的新访客。[人脸识别事件](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/EventNotify/FaceRecognitionEvents.html)。

实施前需要用同一名登记人员验证：照片接口的 `FaceUUID`，实际回调的 `personId`、`uniqueId`，以及回调脸库字段之间如何对应。项目当前只保存 FaceUUID，不能未经核对便认定它一定等于某个回调字段。应通过设备序列号限定身份范围，映射到后台 staffId 后再统计；姓名不应作为关联键。

还需要核对多候选匹配的实际报文形态。`matchNumber` 表示识别候选数量，不是本次进入人数；不能直接累计该字段。无法唯一关联的识别结果应保留为待确认状态。

文档中的 FaceReco ACK 与 FaceSnapshot ACK 字段不同，而且人员 ID 的示例类型存在差异。现有抓拍 ACK 不能直接复用为识别 ACK；需要以真实报文和设备验收确认响应字段、类型及重传停止条件。[人脸识别事件](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/EventNotify/FaceRecognitionEvents.html)。

### 3.3 开启回传需要同时满足设备能力、设备配置和后台策略

应先读取现场 `/System/DeviceCap` 及适用的 AI 能力，确认实际通道人脸抓拍、比对和客流功能。再核实人脸识别开关、目标脸库、规则和布防时间；最后由后台心跳策略允许对应事件上报。仅开启后台 `isPersonInfoEnable` 并不能补足设备本身不支持或未开启的功能。[设备能力定义](http://cap.p6sai.com/DeviceCap.htm)、[人脸基本配置](http://p6scgi-api.p6sai.com:4999/web/#/663863654/149227022)、[识别规则](http://p6scgi-api.p6sai.com:4999/web/#/663863654/149227024)、[心跳策略](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/HeartbeatEvent.html)。

必须现场验证工作人员与陌生人是否都产生所需回调，不能只验证工作人员命中。告警规则、APP 推送开关与 HTTP 事件策略的作用需要分别确认，不能把打开某个告警选项当成所有协议已启用。

### 3.4 三种人数口径不能互相替代

| 事件 | 文档主要内容 | 可以表达的指标 | 不能直接证明的能力 |
| --- | --- | --- | --- |
| FaceReco | 单次识别及匹配人员 | 已知身份出现记录 | 陌生人的全天稳定身份 |
| PassengerFlowStatics | 时间段内 inNumber、outNumber | 进出流量；重复进出如何计入需实测 | 全天独立访客数、已排除工作人员的客流 |
| PeopleNumberStatistics | 区域及区域内 PersonNumber | 区域内人数快照 | 当天累计来过多少不同的人 |

客流事件与心跳策略的统计间隔单位为小时。该文档没有给出秒级独立访客总数上报的承诺。区域人数是周期上报，也不能按周期累加为全天客流。[客流统计事件](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/EventNotify/PassengerFlowStatisticsEvents.html)、[区域人数统计事件](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/EventNotify/PeopleNumberStatisticsEvent.html)、[心跳策略](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/HeartbeatEvent.html)。

识别事件的方向字段在文档中固定为 `none`；抓拍事件虽定义进出方向，仍需要验证现场设备能否可靠输出。因此“当天被识别到”与“当天实际进入”应分别定义，不能把看到人脸直接作为入馆证据。[人脸识别事件](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/EventNotify/FaceRecognitionEvents.html)、[人脸抓拍事件](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/EventNotify/FaceSnapshotEvent.html)。

### 3.5 识别间隔、trackId 和图片摘要均不能完成全天去重

文档中的人脸识别间隔配置为 2～15 秒，位于面板机功能接口目录；该设置需要设备支持，也不等价于全天一次。抓拍配置的最大筛选时长属于抓拍过程的筛选参数，同样没有全天身份去重承诺。[识别间隔](http://p6scgi-api.p6sai.com:4999/web/#/663863654/149226679)、[抓拍配置](http://p6scgi-api.p6sai.com:4999/web/#/663863654/149227113)。

`trackId` 的文档定义只覆盖某张图里的某张脸。图片 MD5/SHA-256 标识图片字节，同一人不同角度的照片摘要通常不同。HTTP 事件示例中的 `faceFeature` 是年龄、性别、质量、姿态等属性，没有展示可直接做人脸向量检索的完整契约。[人脸抓拍事件](http://docs.p6sai.com/docs/cn/device/Event/http/httphttps/Event/EventNotify/FaceSnapshotEvent.html)。

另一个值得继续向厂商确认的入口是抓拍配置 `IsPushFaceFeatures`，能力定义中也有人脸特征推送相关项。但这些开关名称不足以证明 HTTP 可以获取可比较向量。若要据此实现访客去重，必须拿到实际载荷、模型版本、相似度计算方法、阈值和跨设备适用范围。[抓拍配置](http://p6scgi-api.p6sai.com:4999/web/#/663863654/149227113)、[能力定义](http://cap.p6sai.com/DeviceCap.htm)。

## 4. 适合当前项目的实现方案

### 4.1 工作人员识别和日去重：优先实施

建议的数据流是：

```text
后台工作人员维护
    → 设备脸库同步成功
    → 本地人员及设备身份关联提交

设备采集人脸并比对
    → FaceReco 回调
    → 保存事件并解析设备身份
    → 映射本地 staffId
    → 按 hallId + businessDate + staffId 去重
    → 大屏读取当天识别到的工作人员人数
```

这样工作人员识别在设备侧执行，Java 后台只做协议解析、身份映射和数据库去重，不需要为工作人员再引入本地人脸模型。

建议新增最少的数据结构：

| 数据 | 建议保存的内容 | 作用 |
| --- | --- | --- |
| 识别事件 | 来源设备、事件编号和时间、人员身份字段、分数、处理状态、关联 staffId、协议必要字段 | 幂等、审计及未映射事件后续处理 |
| 每日工作人员记录 | hallId、businessDate、staffId、firstSeenAt、lastSeenAt | 每名工作人员每天一条，持久化去重 |

每日记录使用 `UNIQUE(hall_id,business_date,staff_id)` 约束；重复出现仅更新首次/末次时间。人员规模较小时，直接统计每日记录条数即可，暂不必再维护一张可能与明细失配的汇总表。

必须分别处理两层去重：第一层拦截同一事件重传，第二层合并同一人员当天的不同事件。日期以 `info.time` 转换到 Asia/Shanghai 后确定，不能以回调接收日期替代；午夜不必清空一张全局计数表，查询新日期即可。后台重启也应继续使用持久化记录。

设备同步先于本地提交，还存在短暂的身份映射窗口：新人员已在设备生效，识别回调可能先于本地绑定提交到达。这是根据当前代码顺序推导的情况。应将此类结果保存为 `UNMAPPED` 并允许稍后重新关联，不能立即当成陌生访客计数。

若设备有多个候选、人员身份未知或比对有效性不明确，应先保留为待处理记录；不要使用姓名兜底关联。统计历史也不应因后台后来删除工作人员而直接丢失，可以保留必要的事件时分类信息。

### 4.2 普通访客：先确定可信身份来源

访客没有预登记照片时，设备与工作人员库比对失败，只能说明未命中该库。它可能是新访客、回访访客，也可能是工作人员漏识别。因此“未匹配次数”不能直接解释为“去重访客人数”。

可选择的路径及成立条件如下：

| 路径 | 对当前项目的影响 | 成立条件 |
| --- | --- | --- |
| 厂商设备原生日去重或稳定匿名身份 | 最符合设备侧识别的方向 | 提供真实接口、去重范围、日界线、重启及跨设备行为 |
| 设备输出可比较的人脸特征，后台只比较特征 | 无需后台重新从照片提取特征，但仍需身份聚类逻辑 | 完整特征协议、合法模型版本和比较方法已确认 |
| 独立人脸服务对访客抓拍建模、匹配当天身份 | 新增算法服务和日访客身份库，超出现有实现 | 接受新增识别能力，完成速度与准确率验收 |
| 所有访客事先登记或使用稳定凭证 | 可以按业务身份去重 | 业务流程允许登记或提供其他稳定身份 |
| 只展示设备进出流量 | 后台开发量相对较小 | 接受指标为进出人次，不能标成日去重人数 |

把陌生人首次抓拍自动加入“当日访客库”只能作为待验证实验方案：需要解决设备建模速度、尚未建模时重复抓拍、人员上限、清库与迟到补传、多个库之间匹配以及照片规格问题。当前代码和文档没有验证这条完整链路，不建议直接按已可用能力承诺。

### 4.3 不要混算工作人员人数和设备进出人次

例如同一工作人员一天进入 10 次，工作人员去重数为 1，进出统计中可能包含 10 次进入。用“总进入人次减工作人员去重人数”会残留 9 次工作人员流量，所得值不能叫访客人数。

只有来源覆盖、方向、时间范围和去重口径相同，且工作人员与访客分类可靠时，才可以求和或相减。工作人员识别漏报会影响访客分类，后续识别成功时还可能需要纠正当天先前的分类；后台日去重无法修复设备从未捕获或一直认错的身份。

## 5. 最小改动清单与推进顺序

| 顺序 | 改动或验证 | 主要位置 | 完成标准 |
| --- | --- | --- | --- |
| 1 | 真实人员照片新增、更新、停用、重新启用、删除 | 现有人员同步链路 | 页面操作、本地记录和设备人脸身份一致 |
| 2 | 获取设备能力及脱敏 FaceReco 样本 | 现场设备只读核对与回调抓取 | 确认身份映射、陌生人、候选数量、ACK 和重传 |
| 3 | 接收并持久化 FaceReco，再开启心跳识别策略 | DeviceEventService、DeviceController、Models、Mapper、schema | 已知人员、未知人员、重复与并发回调均正确处理 |
| 4 | 新增工作人员日去重记录 | 新的统计服务和 Mapper | 同人同日一次、跨日各一次、重启不丢失 |
| 5 | 输出工作人员统计与最近识别资料 | ScreenController | 实时展示已确认来源和正确人数口径 |
| 6 | 按业务需要单独接入进出/区域人数事件 | 独立事件处理分支 | 区间流量、区域快照与识别人数分别展示 |
| 7 | 确认并实施访客身份方案 | 由设备能力决定 | 真机验证跨次、跨时段和跨设备的去重效果 |

实现时可继续复用现有配置、时间解析、图片存储、事件持久化和设备客户端。接收逻辑和统计逻辑应分开；只有事件已可靠保存后再发送 ACK。如果需要异步处理，应同时持久化处理状态或待处理任务，避免 ACK 后仅留在内存导致统计丢失。

原有“建议每 2 秒轮询大屏”可以继续使用，先测量识别到展示的实际延迟，再决定是否需要 SSE/WebSocket。设备处理、网络、落库和轮询都影响延迟，没有真机测试前不承诺固定实时性。

批量同步方面，当前每次人员变更都查询设备人员列表，新增后还需再次查询。脸库人数较多或批量导入时需测量耗时；在身份契约未确认前，不宜为了提速跳过这些核对。

## 6. 真机验收与厂商确认项

### 6.1 需要厂商明确回答的问题

1. 具体型号、固件版本能否同时开启人脸抓拍、人脸比对和客流统计？是否存在算法资源互斥？
2. 照片新增时 FaceUUID 应为空还是由平台生成？实际回调哪个字段与之对应？
3. 工作人员命中和陌生人未命中，是否都会发送 FaceReco？规则和心跳策略分别怎样设置？
4. FaceReco ACK 必须包含哪些字段、类型是什么？陌生人时如何应答？
5. “去重”若由设备支持，范围是当前跟踪过程、几秒、可配置时间窗还是自然日？离开一小时返回是否仍算同人？
6. 是否能提供稳定匿名访客 ID 或可比较特征？`IsPushFaceFeatures` 对 HTTP 到底产生什么载荷？
7. 断网和断电缓存容量、保留时长、恢复后的重传顺序与事件标识规则是什么？
8. 多设备之间是否共享身份或仅各自统计？如果上传汇总值，重复窗口和更正值如何处理？
9. 进出流量的统计区间是增量还是累计，有无重叠窗口，跨午夜区间如何归属？

文档提供识别历史记录查询接口，可作为补取方案的候选，但其适用设备、存储要求和身份字段均需确认，不能直接认定任何 IPC 都支持或查询结果能无损替代 HTTP 回调。[识别记录查询](http://p6scgi-api.p6sai.com:4999/web/#/663863654/149227020)。

### 6.2 建议验收场景

| 场景 | 预期 |
| --- | --- |
| 登记工作人员站在镜头前连续被抓拍 | 日工作人员数只增加 1 |
| 同人离开后在半小时、数小时后返回 | 当天不再增加 |
| 多名工作人员同名 | 通过身份字段准确关联，不按姓名合并 |
| 后台重启、设备重启、回调并发或重传 | 不丢记录、不重复计数 |
| 午夜前发生、午夜后补传 | 归属原事件日期 |
| 陌生访客同日多次返回 | 只有选定身份方案经过验证后才承诺计 1 |
| 工作人员第一次漏识别、后续识别成功 | 不将同人永久拆成工作人员和访客两人 |
| 同人经过两台摄像头 | 全馆口径能合并；设备局部编号不能直接跨设备使用 |
| 设备已成功写入、后台提交失败 | 补偿可验证，失败时能明确标出需对账 |
| 多人同行、侧脸、背光、遮挡及远距离 | 测量漏检和误认，说明指标实际覆盖范围 |

软件唯一键可以保证相同业务身份在同一天只保存一条，但不能保证人脸算法对同一个人始终返回相同正确身份。需分别验收计数幂等、身份准确率、漏报率和显示延迟。

## 7. 证据范围

本次进行了源码与 SQL 静态检查、厂商公开网页读取及既有验证记录检查，只更新分析文档，未修改业务代码、未调用现场设备、未运行测试或写入业务数据库。既有测试及真机诊断仅作为历史证据，不证明尚未实现的 FaceReco 接入和全部人员日去重。

本次成功读取了脸库管理指导、人脸识别、人脸抓拍、客流统计、区域人数、心跳策略、无认证配置、HTTP 常见问题及设备能力定义。详细参数站的浏览器访问因自动审批服务返回 403 而被拦截，未继续登录或通过其他路径绕过。其详细参数引用来自仓库既有清单，不能写成本次重新验证；尤其不能据特征推送开关名称断言已取得可比较的人脸向量。

工作人员同步成功、FaceReco 身份核对和工作人员日去重可作为阶段成果；完整需求的关键路径是先验证陌生访客的身份来源，再完成统一日去重。在此之前，大屏全部人员日去重及访客日去重应继续表达为暂无可信统计来源。

## 8. 全部到访人员日去重的落地方案

### 8.1 业务指标和完整可行性结论

建议指标定义为：在北京时间自然日内，进入展厅统计范围、被有效采集并归并为同一身份的人员，每人计一次；包括工作人员与未登记访客。若目前只能采集镜头前的人脸，指标应描述为当日识别到的独立人员，直到入口覆盖、进入方向及漏检率经过验收后，再将其解释为实际到访人数。

同一人在上午和下午分别到访，当天合计 1 人；第二天再次到访，第二天再计 1 人。人员离馆不减少当日累计数。区域当前人数以及进出人次分别计算，不与当日去重人数共用一套累加公式。

仅用“工作人员库比对 + 未命中事件 + 设备进出数量”无法推导全部到访人员日去重数。完整目标还必须具备以下至少一种身份来源：设备提供覆盖全天的稳定访客 ID、设备提供带比较方法的可用特征、独立算法服务从抓拍照片产生可比较特征，或业务提供稳定凭证。

### 8.2 推荐的数据流及职责

```text
后台维护工作人员
    → 同步设备人员资料与照片
    → 保存本地人员及设备身份关联

设备采集人脸
    → 设备比对工作人员库
    → 回调事件可靠落库，持久化待处理状态，再 ACK
    → 关联已确认的工作人员身份
    → 对未确认人员使用选定的访客身份能力
    → 在全馆、当天范围内查找或创建统一人员身份
    → 幂等更新每日到访记录
    → 后端统计接口输出工作人员、访客、总人数及处理状态
    → 大屏轮询或订阅更新
```

如果设备确有原生日去重汇总能力，也可由设备上报权威汇总值，但必须约定时间范围、身份覆盖、重启恢复、更正及多设备合并语义。否则优先由设备上传事件、后台统一计算；“将统计发送后端”在这一实现中就是后端接收身份事件后产生统计，不需要设备先算出一个当前协议没有承诺的日去重总数。

### 8.3 三条主要技术路径

| 路径 | 必须拿到的证据 | 与现有项目的关系 | 决策建议 |
| --- | --- | --- | --- |
| 设备原生日去重、稳定匿名访客 ID 或权威汇总 | 固件型号、真实回调、同人相隔数小时仍同 ID、重启及跨设备说明 | 最符合设备侧完成算法的方向，Java 主要解析、持久化和统计 | 优先向厂商核实；当前未证明具备 |
| 设备输出可比较特征，后台做当日检索 | 特征载荷、编码、模型版本、比较算法或厂商 SDK、阈值及授权条件 | 可复用 Java 事件接收和数据库，新增访客检索及聚类 | 只有开关或字段名不足以立项承诺 |
| 独立算法服务处理抓拍照片 | 模型或服务可用、部署资源、速度、误认和漏认验收 | 当前项目已移除该类能力，需要重新引入服务和每日身份模板 | 厂商不提供前两项、仍坚持全部人员日去重时的主要替代路径 |

独立算法部署在本地还是远端可另行选择，本次不假定允许把抓拍照片上传第三方。工作人员设备识别也可继续使用，访客算法通过独立服务接口接入，避免把模型运行时直接塞进 Java 8 业务服务。

若要求工作人员首次漏识别、后续命中时仍保持总数正确，需要为漏识别期间的匿名身份保留可关联依据，并支持合并；若算法服务仅处理未命中照片，而后续只得到工作人员 ID、无法比较两次采集，则这一纠正能力仍然缺失。

### 8.4 最少数据及并发要求

以下为建议结构，不是当前已经存在的表或接口：

| 数据 | 建议内容 | 复用及设计要求 |
| --- | --- | --- |
| 设备人员映射 | 设备、脸库、设备身份、本地 staffId、有效区间 | 复用 `exh_staff_device`；停用/删除会删除当前绑定，若要处理此前的迟到事件，应保留历史身份别名 |
| 身份事件 | 事件幂等键、发生及接收时间、设备身份、图片引用、候选与分数、处理状态、最终人员身份 | 复用现有接收与图片组件；FaceReco 与 FaceSnapshot 不应因来自同人便被误判为同一个协议事件 |
| 每日人员身份及到访 | hallId、businessDate、subjectId、人员类别、staffId、首次/末次时间、身份来源 | 每人每天一条，唯一键为 `(hall_id,business_date,subject_id)`，初期可直接 COUNT 避免多存汇总 |
| 访客模板 | 关联每日身份、特征或可比较模板、模型版本、质量、必要图像引用 | 只在选定的技术路径需要时新增；普通照片摘要不能充当人脸特征 |

事件幂等解决同一事件重传；每日唯一键解决同一已知身份重复到访。陌生人的身份生成还多一步：先相似度查找、未命中再创建。当同人的两张照片并发到达时，两条任务可能同时查不到，分别创建两个 subjectId，此时唯一键仍会全部通过。

当前单实例可按展厅和业务日期串行执行“查找/建身份/登记”；未来多实例需使用跨实例串行队列或数据库协调机制。串行粒度和吞吐量应实测，不能把数据库唯一键当作相似度聚类的并发保护。

工作人员和访客使用统一日身份或明确的身份合并机制。若首次未命中产生匿名记录，稍后确认属于当天已有工作人员，应合并身份并更正类别，避免工作人员数和访客数各计一次。临界分数、照片质量不足或多候选冲突应记录待确认，不能默认每条异常都是新访客。

### 8.5 当前项目需要调整的位置

| 改动 | 当前基础 | 必须完成的行为 |
| --- | --- | --- |
| 统一新增人员身份契约 | CREATE 分支传随机 FaceUUID，与说明不同 | 真机确认新增、回读、建模和 FaceReco 身份映射；随后统一说明与注释 |
| 支持 FaceReco 及专用 ACK | `DeviceController`、`DeviceEventService` 仅接收心跳和抓拍 | 解析匹配、陌生人和身份字段；先可靠保存再按实机协议 ACK |
| 开启识别事件策略 | 心跳 `isPersonInfoEnable=false` | 接收逻辑准备就绪后开启，并确认设备识别规则及 HTTP 平台配置 |
| 接入访客身份能力 | 无当前可用的特征服务或稳定访客身份 | 从 8.3 选定并验收一条路径；不能只新增 visitorId 随机数 |
| 实现统一日去重 | 无每日身份表和统计服务 | 事件幂等、相似度并发保护、每日唯一约束、分类及身份合并 |
| 输出真实统计 | `ScreenController.overview()` 固定无人数 | 返回统计模式、范围、日期、人数、更新时间和必要处理状态；对未具备的数据保持未知 |
| 可靠补传与恢复 | 抓拍已支持持久化及过期标记 | 异步任务可重试、重启续跑；迟到事件归属发生日，图片/模板保留覆盖允许补传期 |

现有人员同步顺序可以沿用，但设备与 MySQL 无原子事务。若业务要求设备离线仍能先维护本地人员，则需要额外引入待同步状态、持久化任务和对账；当前“设备失败则本地不提交”的行为不满足离线先维护的要求。这是业务选择，本次不改同步流程。

### 8.6 实时性、准确率及容量

实时展示延迟由设备采集/识别、回调传输、队列、特征处理、数据库及大屏刷新组成。现有大屏接口建议 2 秒轮询，可先沿用；只有实测证明瓶颈在展示刷新时再考虑 SSE/WebSocket。官方客流事件的小时统计间隔不能用作秒级日去重展示的保证。

人脸日去重本质上有误认、漏认和漏检：阈值过严可能将同人拆为多人，阈值过松可能合并不同人。需要分别测量入场采集覆盖、身份准确性、重复计数率及延迟。软件去重只能约束已获得的身份，不能补回没有采集到的人。

容量应按峰值事件速率、每次处理耗时、每天独立人员数和实际图片大小估算。例：平均每秒 1 条事件、每天有效采集 10 小时，即 36000 条；若每条保留图片合计 100 KB，约 3.6 GB/天，30 天约 108 GB，未计数据库、索引、备份及额外图片。此为规划示例，不是现场测量值。后台照片保存、设备识别及向量检索应分别测量吞吐。

### 8.7 全部人员口径的验收门槛

| 场景 | 预期 |
| --- | --- |
| 未登记访客 A 上午、下午、闭馆前各到访一次 | 当天总数只增加 1 |
| 同一访客第二天再来 | 第二天增加 1，前一天不变 |
| 两名相貌相近访客、双人同行 | 分别计数，记录算法误差与漏检 |
| 同一陌生人的首次照片并发到达 | 只创建一个当日人员身份 |
| 工作人员第一次未命中、随后准确命中 | 当日总人数不因身份类别更正重复增加 |
| FaceSnapshot、FaceReco 均上报，且各自重传 | 协议事件可分别保存，同一人每天仍只计一次 |
| 23:59 发生、次日 00:05 补传 | 归属前一天，首次/末次时间正确 |
| 工作人员停用/删除后补传此前事件 | 能按事件时间关联历史身份，避免误计为新访客 |
| 后端/设备重启、网络中断再恢复 | 检查是否存在丢失、重复、新身份及长期积压 |
| 同人经过多个入口或多个设备 | 全馆统一去重；不能直接相加设备独立日人数 |

建议实施顺序为：先获取真实设备能力与事件样本，并用陌生访客相隔数小时再次出现验证身份来源；同时验收已有工作人员同步；身份路径明确后实现 FaceReco、统一日身份和统计输出，最后完成上述场景的准确率与延迟验收。仅完成工作人员闭环应标记为阶段成果，不作为全部到访人员日去重验收通过。
